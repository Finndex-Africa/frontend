# Internationalization (English / French)

Both apps use [`next-intl`](https://next-intl.dev) v4. They share the same
message-catalog format but differ in how the active locale is carried.

| | `frontend` (public) | `dashboard` (admin) |
|---|---|---|
| Locale in URL | **Yes** — `/en/…`, `/fr/…` | No — URLs unchanged |
| Source of truth | URL segment (+ `NEXT_LOCALE` cookie for redirects) | `NEXT_LOCALE` cookie only |
| Why | French pages must be independently indexable and shareable | Admin tool, no SEO; keeps the auth middleware untouched |
| Switcher | `src/components/global/LanguageSwitcher.tsx` (navbar) | `src/components/global/LanguageSwitcher.tsx` (sidebar, drawer, settings) |

## Adding a translated string

**1. Add the key to both catalogs.** They must stay in lockstep — `check-i18n`
fails the build otherwise.

```jsonc
// messages/en.json           // messages/fr.json
"bookings": {                 "bookings": {
  "confirmTitle": "Confirm"     "confirmTitle": "Confirmer"
}                             }
```

**2. Use it in the component.**

```tsx
import { useTranslations } from "next-intl";

export default function BookingCard() {
  const t = useTranslations("bookings");
  return <h2>{t("confirmTitle")}</h2>;
}
```

In a **server component**, use the async form instead:

```tsx
import { getTranslations } from "next-intl/server";

const t = await getTranslations("bookings");
```

**3. Verify.**

```bash
node scripts/check-i18n.mjs
```

### Interpolation and plurals

```jsonc
"greeting": "Hello {name}",
"bedrooms": "{count, plural, one {# bedroom} other {# bedrooms}}"
```

```tsx
t("greeting", { name: user.firstName })
t("bedrooms", { count: 3 })
```

> **Numbers that aren't quantities** (years, IDs, phone numbers) must be passed
> as **strings**, or ICU will group them — `2026` renders as `2 026` in French.
> See `footer.copyright` for the pattern.

### Embedded markup

Use `t.rich` rather than splitting a sentence across keys — word order differs
between languages.

```jsonc
"welcome": "Welcome to <b>FindAfriq</b>."
```

```tsx
{t.rich("welcome", { b: (chunks) => <span className="font-semibold">{chunks}</span> })}
```

## Navigation (frontend only)

Because the frontend puts the locale in the URL, **import navigation helpers
from `@/i18n/navigation`, not from `next/link` / `next/navigation`**:

```tsx
import { Link, useRouter, usePathname, redirect } from "@/i18n/navigation";
```

These keep the active locale in every URL automatically. `usePathname` returns
the path *without* the prefix, so `/routes/login` stays `/routes/login` on both
`/en` and `/fr` — which is why the `ConditionalNavbar` / `MobileBottomNav`
path checks still work.

Using plain `next/link` will drop the user back to the default locale.

The dashboard has no locale prefix, so it keeps using `next/link` and
`next/navigation` as before.

## Backend enum values (property types, categories, units)

`propertyType` is free-text on the backend and categories are snake_case, so
listing data arrives as `"house"`, `"House"`, `"Office Space"`,
`"painting_decoration"`. Don't render these raw — run them through the
normalizing lookup, which falls back to a humanized version of the raw value
when there's no catalog entry (so a new server-side type degrades gracefully
instead of throwing):

```tsx
import { useEnumLabel } from "@/lib/enum-labels";

const propertyType = useEnumLabel("propertyTypes");
propertyType("house");          // "House" / "Maison"
propertyType("geodesic_dome");  // "Geodesic Dome" (no entry → humanized)
```

Namespaces: `propertyTypes`, `serviceCategories`, `buySellCategories`.

Phrases built *around* a value must be whole ICU messages, not concatenation —
English "House for rent" is French "Maison à louer", so the word order differs:

```jsonc
"forRent": "{type} for rent"     // en
"forRent": "{type} à louer"      // fr
```

## Dates, numbers, currency

Never hardcode `toLocaleDateString("en-US", …)`. Use the shared helper:

```tsx
import { useFormat } from "@/lib/format";

const fmt = useFormat();
fmt.date(booking.scheduledDate);              // 12 Mar 2026 / 12 mars 2026
fmt.dateTime(message.createdAt);
fmt.currency(property.price);                 // $1,200 / 1 200 $US
fmt.number(stats.total);
fmt.relativeTime(notification.createdAt);     // 2 days ago / il y a 2 jours
```

Antd's own strings (pagination, empty states, date pickers) are wired in
`dashboard/src/components/LayoutClientWrapper.tsx` via `ConfigProvider locale`.

## Adding a third locale

1. Add the code to `locales` in `src/i18n/routing.ts` (both apps) and give it a
   `localeNames` entry.
2. Create `messages/<code>.json` — copy `en.json` and translate.
3. Frontend only: add `localeHtmlLang` / `localeOgTag` entries, and the
   `alternates.languages` map in `src/app/[locale]/layout.tsx`.
4. Dashboard only: add the matching antd locale to `ANTD_LOCALES`.
5. Run `node scripts/check-i18n.mjs` in both apps.

`sitemap.ts` and `robots.ts` iterate `routing.locales`, so they pick up new
locales with no further edits.

## What is and isn't translated yet

### Done

**The whole public frontend is translated.** Navigation, home, all browse pages,
all listing detail pages, account pages, create/edit forms, content pages,
reviews, modals, toasts, validation messages, and page metadata.

Backend enum values (property types, service categories, amenities, buy-and-sell
subcategories, land units, owner roles) resolve through `useEnumLabel`, with a
humanized fallback for values not yet in the catalog.

**Legal pages** (terms, privacy, platform policy) are translated and carry a
`LegalTranslationNotice` stating that the English version prevails — see below.

### Not translated, deliberately

- **Dead code.** These have zero importers and were skipped: `config/navigation.tsx`,
  `components/dashboard/{DashboardLayout,PropertyForm,PropertiesTable,ServicesTable}.tsx`,
  `components/modals/FeedbackModal.tsx`. Delete them or translate them if revived.
- **Brand names.** FindAfriq, Facebook, WhatsApp, LinkedIn, YouTube, X (Twitter).
- **User-generated content.** Listing titles, descriptions and review bodies go
  through the machine-translation pipeline, not these catalogs.

## API and network errors

`lib/error-messages.ts` resolves an error to a *catalog key*, and
`useErrorMessage()` translates it:

```tsx
import { useErrorMessage } from "@/lib/error-messages";

const errorMessage = useErrorMessage();
toast.error(errorMessage(error, "createProperty"));
```

The second argument names an entry under `errors.fallback` — used only when
nothing more specific matched. Resolution order:

1. **Network / timeout** — axios `ERR_NETWORK`, `ECONNABORTED`, "Network Error",
   "Failed to fetch". This is what used to leak the raw English "Network Error".
2. **Known upload errors** — the API phrases these several ways; aliased onto
   one key each (`errors.upload`).
3. **Known backend messages** — 36 of them mapped under `errors.server`,
   keyed by a normalized slug ("Property not found" → `property_not_found`).
4. **Unrecognised backend text** — shown verbatim. See the caveat below.
5. **HTTP status** — `errors.status.{400,401,403,404,413,422,500}`.
6. **The caller's fallback key.**

### Caveat: unmapped backend messages stay English

The backend has no i18n, so a message it returns that isn't in `errors.server`
is displayed as-is. That's deliberate — showing "Refund amount exceeds payment
amount" beats replacing it with a vague translated "Something went wrong."

Two ways to close the gap, in order of preference:

1. **Have the API return error *codes*** (`{ code: "REFUND_EXCEEDS_PAYMENT" }`)
   alongside the message; the frontend then owns all copy. This is the real fix.
2. Add the message to `errors.server` in both catalogs. Cheap, but it drifts the
   moment someone edits the string on the backend.

`resolveError()` is exported and pure, so this is unit-testable without React.

### Legal pages need review before the French is authoritative

`terms`, `privacy` and `platform-policy` are binding documents. The French is a
careful translation but has **not** been reviewed by a lawyer or a certified
legal translator, so each French page renders this notice:

> Cette traduction est fournie à titre indicatif. En cas de divergence, la
> version anglaise fait foi.

That is standard practice and is what makes shipping the translation safe. If
you want the French to be authoritative, get it reviewed and remove the notice
by clearing `legal.translationNotice` in `messages/fr.json`.

### Known limitation### Known limitation

Locale is **per-browser**, not per-account. A user's choice lives in the
`NEXT_LOCALE` cookie and does not follow them across devices. Persisting a
`preferredLanguage` on the user record and seeding the cookie at login would
fix that — backend change, not done here.

## User-generated listing text (Airbnb Translation Engine parity)

Message catalogs can't translate landlord-authored titles and descriptions —
that text lives in the database. This follows the same model as [Airbnb's
Translation Engine](https://slator.com/airbnb-translation-engine-applies-machine-translation-to-ugc/).

### The three rules we copied from Airbnb

1. **Automatic, not click-to-translate.** The translation is what renders.
2. **Inverted UX.** A "Show original" button, not a "Translate this" button.
3. **Never overwrite the author.** If the author already wrote in the viewer's
   language (`sourceLang === locale`), or supplied their own translation
   (`translationSource: 'human'`), the original is served untouched. This is
   the [documented Airbnb complaint](https://community.withairbnb.com/t5/Ask-about-your-listing/Airbnb-automatically-translates-listing-despite-proper/td-p/2081284)
   we designed around.

### Backend — `backend/src/modules/translation/`

Translation happens **on save**, not on view. That's a deliberate divergence
from Airbnb: because our French URLs are indexable, French HTML has to be
server-rendered rather than filled in on first visit.

```
translation.types.ts             TranslationProvider interface + shared types
providers/modernmt.provider.ts   ModernMT — the engine Airbnb runs on
translation.service.ts           orchestration, guards, detection
translation.module.ts            @Global, provider selected by env
```

Stored on `Property`, `Service`, `BuySellListing` and `Review`:

```ts
sourceLang?: string                   // detected on save
translations?: { fr: { <field>: string } }
translationSource?: 'machine' | 'human'
translatedAt?: Date
```

Translatable fields are per-entity, not hardcoded:

| Entity | Fields |
|---|---|
| Property / Service / BuySellListing | `title`, `description` |
| Review | `text`, `ownerReply` |

Wired into `create()` and `update()` on all four services, plus the review
reply path — Airbnb translates host responses alongside the review body.
`update()` only re-translates when the author text actually changed, so editing
a price or a rating doesn't burn API quota.

**Translation failure never blocks a save.** `buildTranslations()` returns
`null` on error and logs; the listing is written regardless.

### Config

```bash
TRANSLATION_PROVIDER=modernmt
MODERNMT_API_KEY=...              # unset => translation silently disabled
```

To swap engines (DeepL, Google), implement `TranslationProvider` and add a case
to the factory in `translation.module.ts`. Nothing else changes.

### Backfill

Existing listings have no translations. Run once:

```bash
cd backend
pnpm backfill:translations -- --dry-run --limit=10   # inspect first
pnpm backfill:translations                           # all collections
pnpm backfill:translations -- --only=properties
pnpm backfill:translations -- --only=reviews
```

Collections: `properties`, `services`, `buy-sell`, `reviews`. Reviews are by
far the highest-volume one — run it with `--limit` first to gauge cost.

Resumable — documents with `translatedAt` are skipped, so re-running after an
interruption picks up where it stopped.

### Frontend

```tsx
import { useTranslatedContent } from "@/lib/translated-content";
import TranslatedText from "@/components/ui/TranslatedText";

const translated = useTranslatedContent(property);

<TranslatedText text={translated.title} as="h1" className="..." />
<TranslatedText text={translated.description} />
```

`TranslatedText` renders the translation with a
`Traduit automatiquement · Voir l'original` disclosure. When the text isn't a
machine translation it renders plain, with no disclosure at all.

For entities whose fields aren't `title`/`description`:

```tsx
import { useTranslatedFields } from "@/lib/translated-content";

const translated = useTranslatedFields(review, ["text", "ownerReply"] as const);
<TranslatedText text={translated.text} />
<TranslatedText text={translated.ownerReply} />
```

**Cards vs detail pages:** listing cards show the translated title *silently*
(no disclosure) — same split Airbnb uses between search results and the listing
page. Detail pages and reviews carry the banner.

## Checks

```bash
# in either app
pnpm check:i18n
```

Verifies that every locale file has an identical key set, and that every
`t("…")` call in `src/` resolves to a key that actually exists. Worth wiring
into CI alongside `tsc --noEmit`.

### Two dev-server gotchas

> The checker's `CALL` regex must include `_` (`/\b(t[A-Za-z_0-9]*)\(/`) or it
> silently skips every `t_<namespace>(...)` call and reports OK while validating
> nothing. Both apps use that naming.

**Raw key paths rendering** (`propertyDetail.aboutThisPlace` instead of
"About this place") means the messages module is stale, not that the key is
missing. `messages/*.json` is loaded through a dynamic `import()` in
`src/i18n/request.ts`, and Next's dev server caches it — adding a **new
top-level namespace** while the server is running doesn't reliably invalidate
that cache. Restart `pnpm dev`. Production builds are unaffected.

**`Cannot find module './vendor-chunks/…'`** means a `next build` ran while
`next dev` was up; they share `.next/`. Stop dev, `rm -rf .next`, restart.
